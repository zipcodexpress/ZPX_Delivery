# Delivery admin site

`apps/admin` is the ThinkPHP presentation and access layer for the delivery system. The existing `apps/api` application loads `routes.php`, renders these Think templates, and shares its PostgreSQL connection, identity sessions, CSRF checks, and domain services. The API Docker image copies this sibling folder; there is no separate admin database or login store.

Open `http://localhost:8000/admin` in local development. The first release includes the dashboard, shipment list, customer shipping restrictions, driver approval and suspension, pickup route assignment, and uncollected-run recovery. It follows the sidebar/topbar, card, table, and form style of `zpxadmin-tp8` without importing apartment-specific models or permissions.

Customer restrictions stop new shipment creation while leaving existing shipment access intact. Driver suspension takes the driver offline, cancels open offers, and blocks new offers; assigned runs and custody remain for explicit recovery. The transition API requires an `If-Match` driver version, and reactivation leaves the driver offline until they opt in again. Migration `022_customer_shipping_restrictions.sql` adds the restriction ledger and driver version.

The customer and driver names open detail pages. Customer detail shows masked contact/verification status, address editing, recent linked shipments, payment attempts and recorded paid/refunded totals. Driver detail shows application and approval timestamps, qualification/availability, assignments, offers, package scans, earnings entries and recorded settlement totals. These are bounded recent lists, not complete paginated histories. The earnings ledger is not a cash account or proof of an external payout. Both pages retain redacted administration action names and times. The corresponding JSON detail endpoints use the same network-admin guard. Search filters, support-case workflow, commercial affiliation, vehicle management and finance reconciliation remain separate backlog work.

The Partners menu is an initial registry, backed by migration `023_partner_registry.sql`. Existing networks receive one internal registry identity with no resource assignments; new synthetic networks receive it during seeding. Network admins can create an audited external `DRAFT` with a code, display name and classification roles. Legal name may remain empty until verified. Registry roles do not grant admin, site, locker, driver, parcel or financial access. Delegated membership/grants, relationship periods and activation remain ADM-04 follow-up work.

Shipment rows now open a lifecycle page that joins the existing shipping, custody, scan, receiving, exception, payment, route, locker-session and pickup-grant records. It distinguishes synthetic assumptions and missing payment evidence. Site and locker directories are separate. Sites contain explicit draft property-owner and host partner links, contract reference and dates, and encrypted operational contacts. Lockers remain bound through their routing location and expose recorded devices, boards, manifests, modules and boxes. Migrations 025 and 026 add this metadata without commissioning hardware or activating contracts. Contact management is a first site-only slice; shared contacts, location overrides, effective-period coverage and contract documents remain for later work.

The access endpoint is `GET /api/delivery/v1/admin/access`. Its capability response is a navigation hint; every server action rechecks identity and the existing service's authorization. Only a network-wide `ADMIN` grant opens this site. Location grants appear as scoped hints but confer no network admin power.

Source ownership: `routes.php` mounts HTML pages, `src/` contains thin page adapters and access resolution, `view/` contains presentation only, and `public/admin.css` is served through `/admin-style`. Business rules stay in the delivery services under `apps/api/src/`.
